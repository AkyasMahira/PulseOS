# AUDIT_LOG.md — PulseOS Security & Technical Audit

> Generated by static analysis of repository. No runtime testing performed.
> Each item is marked: **Fixed** | **Partially Fixed** | **Pending**

---

## 🔴 CRITICAL

---

### C-01 — Stripe Webhook Signature Not Verified
- **Status**: Pending
- **Risk**: Any attacker can POST to `/api/billing/webhook` with a forged Stripe event, upgrading accounts to paid plans or downgrading them without payment.
- **File**: `apps/api/src/routes/billing.ts:131-150`
- **Evidence**: Comment explicitly states "simplified — in prod use stripe SDK". `sig` header is read but never used. No `crypto.createHmac` call.
- **Fix Required**: Use `stripe` npm package and `stripe.webhooks.constructEvent(rawBody, sig, webhookSecret)`.
- **Also required**: Register `@fastify/rawbody` plugin — `rawBody: true` in route config is set but the plugin itself is not registered in `index.ts`.

---

### C-02 — API Keys Stored as Plaintext
- **Status**: Pending
- **Risk**: If `pulseos.db` is ever read (backup leak, directory traversal, VPS compromise), all API keys are exposed in full. Keys should be one-way hashed.
- **File**: `apps/api/src/db/index.ts:308`
- **Evidence**: Comment: "In prod, store bcrypt hash — for simplicity store sha256". Column named `key_hash` but stores the raw `pk_` prefixed key directly.
- **Fix Required**: Store `sha256(key)` in `key_hash`. On lookup, compute `sha256(incoming)` and compare.

---

### C-03 — API Keys Not Used for Authentication
- **Status**: Pending
- **Risk**: API keys can be created and shown to users, but the API never accepts them as auth credentials. This is a broken feature and misleads users.
- **Files**: `apps/api/src/db/index.ts` (`getApiKeyByRaw`, `touchApiKey` defined but never called), `middleware/auth.ts`
- **Fix Required**: Add `x-api-key` header check to `requireAuth` middleware, or create a separate `requireApiKeyOrJwt` middleware.

---

### C-04 — Default JWT Secret in Production
- **Status**: Pending (depends on deployment)
- **Risk**: If `JWT_SECRET` env var is not set, the application starts with `'dev-secret-change-me'` as the JWT signing key. Any attacker who knows this can forge valid JWTs for any user including owners.
- **File**: `apps/api/src/index.ts:21`
- **Fix Required**: At minimum, log a `[WARN]` on startup if secret is default. Ideally, `process.exit(1)` in production if not set.

## 🟠 HIGH

---

### H-01 — Alert Auto-Resolution Not Implemented
- **Status**: Pending
- **Risk**: Functional — alerts fire but `resolvedAt` is never set. The status page `uptime7d` calculation (`SUM(COALESCE(resolved_at, ?) - fired_at)`) will calculate infinite downtime duration for unresolved alerts.
- **File**: `apps/api/src/alerts.ts`
- **Fix Required**: In `tick()` or `evaluateAlerts()`, track which rule IDs are currently firing. When a rule no longer triggers, UPDATE `alert_events SET resolved_at = ? WHERE rule_id = ? AND resolved_at IS NULL`.

### H-02 — Webhook Delivery Never Triggered
- **Status**: Pending
- **Risk**: Functional — users can configure webhooks via the API but they are never called. Feature is silently broken.
- **Files**: `routes/apikeys.ts` (CRUD only), `alerts.ts` (never calls `listWebhooks`)
- **Fix Required**: In `fireAlert()`, call `listWebhooks()`, filter by matching `events` array, POST to each webhook URL with HMAC signature using `secret`.

### H-03 — Plan Limits Not Enforced Server-Side
- **Status**: Pending
- **Risk**: Business — users on the Free plan (1 server, 1 user, 3 alert rules) can add unlimited servers, users, and rules. Entire billing model is bypassable.
- **Files**: `routes/servers.ts`, `routes/team.ts`, `routes/metrics.ts`
- **Fix Required**: In each route, call `getSubscription()` → look up `PLANS[planId].limits` → reject if limit exceeded.

### H-04 — `requireAuth` Does Not Return After `reply.send()`
- **Status**: Pending
- **Risk**: In Fastify, after `reply.send()` the handler can continue executing. If route handler accesses `req.user` after a 401, it will throw.
- **File**: `apps/api/src/middleware/auth.ts:6`
- **Evidence**: `reply.code(401).send(...)` — no `return` statement.
- **Fix Required**: Add `return` before or after `reply.send()`, or re-throw the error.

### H-05 — Disk History Table Never Written
- **Status**: Pending
- **Risk**: Data integrity — `disk_history` table exists with proper schema and indexes, and is pruned, but is never populated. Historical disk usage charts are silently missing data.
- **Files**: `db/index.ts` (table created, pruned), `ws/hub.ts` (only calls `insertMetric`, no disk insert)
- **Fix Required**: Add `insertDiskHistory()` function in `db/index.ts` and call it in `ws/hub.ts:tick()` for each disk in `snapshot.disks`.

### H-06 — Remote Server API Tokens Sent to Frontend
- **Status**: Partially Fixed
- **Risk**: `GET /api/servers` returns server objects from `listServers()` which includes `apiToken`. This should be masked.
- **File**: `routes/servers.ts:68-73`
- **Evidence**: `listServers()` returns `apiToken` field. Route returns `remoteCache.get(s.id)` but falls back to spread of server object including `apiToken`.
- **Fix Required**: Strip `apiToken` from all responses. Never return it after creation.

## 🟡 MEDIUM

---

### M-01 — No Input Validation Beyond Presence Checks
- **Status**: Pending
- **Files**: `routes/team.ts`, `routes/servers.ts`, `routes/apikeys.ts`, `routes/billing.ts`
- **Risk**: Stored XSS via long strings, URL injection in `apiUrl` field for servers, etc.
- **Fix Required**: Add Fastify JSON schema validation to all POST routes (like the login route already has).

### M-02 — JWT Client-Side Role Parsing (Frontend)
- **Status**: Pending
- **File**: `components/layout/Sidebar.tsx:26`
- **Evidence**: `JSON.parse(atob(token.split('.')[1])).role` — manually decoding JWT in browser without verification.
- **Risk**: UI-only — backend enforces roles. But fragile: if token format changes, this silently fails and defaults to 'viewer'. Should use a proper JWT decode library.

### M-03 — No CSRF Protection
- **Status**: Pending
- **Risk**: SPA with JWT in localStorage is not vulnerable to classic CSRF, but cookie-based sessions (if ever added) would be. Rate limiting partially mitigates.

### M-04 — `node-telegram-bot-api` Listed as Dependency But Unused
- **Status**: Pending
- **File**: `apps/api/package.json`
- **Risk**: Supply chain attack surface. Unused dependency.
- **Fix Required**: Remove from `package.json`. Alerts use direct `fetch()` to Telegram API.

### M-05 — In-Memory Alert Cooldown State Lost on Restart
- **Status**: Pending (by design for MVP, but needs documentation)
- **File**: `apps/api/src/alerts.ts:4` (`const lastFired = new Map<string, number>()`)
- **Risk**: After API restart, all alert cooldowns reset. A flapping service could spam notifications immediately after restart.
- **Fix Required**: Persist `lastFired` timestamps to SQLite (add `last_fired_at` column to `alert_rules`).

### M-06 — No Request Body Size Limit
- **Status**: Pending
- **Risk**: Large payloads to any POST endpoint could cause memory pressure on a 2GB VPS.
- **Fix Required**: Add `bodyLimit` to Fastify config in `index.ts` (e.g., `bodyLimit: 1048576` for 1MB).

### M-07 — `@fastify/websocket` Listed But Unused
- **Status**: Pending
- **File**: `apps/api/package.json`
- **Risk**: Unused dependency, potential confusion.
- **Fix Required**: Remove — Socket.IO handles WebSocket transport directly.

### M-08 — No Logging / Audit Trail for Destructive Actions
- **Status**: Pending
- **Risk**: Container stop/restart/delete, user deletion, role changes — none are logged.
- **Fix Required**: Structured log entries or an `audit_log` table.
